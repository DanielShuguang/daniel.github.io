给组件库加上 llms.txt，让 AI 真正读懂你的代码 ​

最近给我们内部的运维组件库做了一件挺有意思的事——给它加了 llms.txt 自动生成功能。趁着思路还热乎，记录一下整个过程。

先聊聊 llms.txt 是个啥 ​

如果你用过 AI 编程助手，应该遇到过这种情况：让 AI 帮你写一段用到内部组件库的代码，结果它给你编了一堆不存在的 Props，或者用法完全不对。

根本原因是 AI 不了解你的组件库。公开的组件库（比如 Ant Design）人家训练数据里有，但你们自己封装的那套内部组件，AI 根本没见过。

llms.txt 就是为了解决这个问题而生的——它是一个专门给 LLM 看的文档文件，把你组件库的 API、Props、用法示例都整理成 AI 最容易消化的格式，放在项目根目录。以后让 AI 帮你写代码前，先把这个文件喂给它，它就知道你的组件长什么样了。

我们的组件库长啥样 ​

我们有一个叫 maintenance 的 React 组件库，专门服务于运维平台。项目结构大概是这样：

├── src/
│   ├── components/         # 组件源码
│   │   ├── index.ts        # 统一导出
│   │   └── <ComponentName>/
│   │       ├── index.tsx   # 组件实现
│   │       ├── type.ts     # TypeScript 类型
│   │       └── demo/       # 示例代码
├── docs/                   # dumi 文档
│   └── <ComponentName>/index.md
└── llms.txt               # 就是我们要生成这个

文档用 dumi 写，构建用 Vite。组件数量不少，手写 llms.txt 显然不现实，所以我们想让它自动生成。

第一版：写个 Node.js 脚本 ​

最初的想法很朴素——写一个 generate-llms-txt.js 脚本，让它自动扫描组件目录，读取文档和类型定义，拼成 llms.txt。

脚本逻辑大概是这样：

  1. 读 package.json 拿包名、版本这些元信息
  2. 读 src/components/index.ts 拿组件列表
  3. 对每个组件，读 docs/<ComponentName>/index.md、type.ts、demo/*.tsx
  4. 拼成统一格式写入 llms.txt

还支持增量更新：脚本会对比组件文件的修改时间和 llms.txt 的生成时间，只重新生成有变化的部分，没变化的直接复用原来的内容。

llms.txt 的格式大概长这样：

markdown
# @du/maintenance-components

> 运维平台 React 组件库

- **版本**: 1.0.0
- **生成时间**: 2026-03-24 14:30:00

## 组件列表 (18 个)

### SomeComponent

组件描述。

**Props:**
- `value` `string` - 当前值
- `onChange` `(val: string) => void` - 变更回调

**类型定义:**
```typescript
interface SomeComponentProps {
  value: string;
  onChange: (val: string) => void;
}
```

**使用示例:**
```tsx
<SomeComponent value="hello" onChange={console.log} />
```

格式非常扁平，AI 读起来没什么障碍。

配合 package.json 也加上对应命令：

json
"scripts": {
  "generate:llms:script": "node ./scripts/generate-llms-txt.js",
  "generate:llms:script:full": "node ./scripts/generate-llms-txt.js --full"
}

这版跑通了，但用了一段时间后发现一个问题：脚本是"机械式"的拼接，生成的文档质量参差不齐。遇到写得比较随意的 Markdown 文档，提取出来的描述就很奇怪，有时候 Props 解析也不准。

第二版：换成让 Claude 来做 ​

既然要给 LLM 读的文档，干脆让 LLM 来写！

我们用的是 Claude Code（就是 Anthropic 出的那个命令行 AI 工具），它有个功能叫 skill——你可以写一个 Markdown 文件描述一个任务的执行步骤，放在 .claude/skills/ 目录下，然后通过命令行调用。

于是写了一个 generate-llms.md skill，告诉 Claude 怎么分析我们的项目结构，怎么生成 llms.txt：

markdown
name: generate-llms
description: 为 React 组件库智能生成 llms.txt 文档，支持增量更新
---

为 React 组件库生成或更新 `llms.txt` 文档文件。

## 执行步骤

1. 读取现有 llms.txt（如果存在），记录已处理组件
2. 分析项目结构：读 package.json、src/components/index.ts
3. 检测变更：哪些组件是新增的，哪些文件改过
4. 增量更新：未变更的保留原内容，变更的重新生成
5. 写入 llms.txt

然后在 package.json 里加上命令，通过 claude CLI 来调用：

json
"scripts": {
  "generate:llms": "claude --dangerously-skip-permissions -p \"增量更新 llms.txt，检测 src/components 和 docs 目录变更，只更新有变化的组件文档，输出到 llms.txt\"",
  "generate:llms:full": "claude --dangerously-skip-permissions -p \"全量重新生成 llms.txt，分析所有组件\""
}

--dangerously-skip-permissions 这个参数是跳过每个操作的确认提示，在自动化场景下是必须的，否则 Claude 每读一个文件都要问你"确定吗"。

这样一来，生成质量明显好多了。Claude 能真正理解组件的用途，生成的描述更自然，Props 的解释也更准确。

第三版：接入 Git Hook 自动触发 ​

手动跑命令还是有点麻烦，理想状态是：我改了组件代码，一提交，文档就自动更新了。

Git Hook + lint-staged 可以做到这个。

配置 .lintstagedrc.js：

js
module.exports = {
  'src/**/*.{js,jsx,ts,tsx}': ['eslint'],
  'src/**/*/*.{less,css}': ['stylelint --fix'],
  // 监听组件和文档变化，使用 AI 增量生成 llms.txt
  '{src/components/**,docs/**}/*.+(ts|tsx|md)': () => {
    return 'pnpm run generate:llms';
  },
};

当你 git commit 的时候，lint-staged 会检查暂存区里有没有组件或文档文件变动。有的话，就自动触发 pnpm run generate:llms，让 Claude 增量更新 llms.txt，然后这个文件也会被一起提交进去。

注意这里有个小细节：lint-staged 的 handler 如果是函数，返回值是要执行的命令字符串，并且这个命令不能依赖传入的文件列表参数。因为我们要全量分析增量变更，让 Claude 自己判断哪些组件需要更新，所以直接忽略 lint-staged 传过来的文件列表，返回固定命令即可。

顺手把 llms.txt 打包进 dist ​

既然要分发给其他项目用，llms.txt 也应该跟着包一起发布。

两个地方要改：

1. package.json 的 files 字段加上它：

json
"files": [
  "dist",
  "llms.txt"
]

2. Vite 构建完后自动复制到 dist：

ts
// vite.config.ts
{
  name: 'copy-llms-txt',
  closeBundle() {
    const fs = require('fs');
    const path = require('path');
    const llmsPath = path.resolve(__dirname, 'llms.txt');
    const distPath = path.resolve(__dirname, 'dist/llms.txt');
    if (fs.existsSync(llmsPath)) {
      fs.copyFileSync(llmsPath, distPath);
      console.log('✅ llms.txt 已复制到 dist 目录');
    }
  },
}

这样发布 npm 包的时候，llms.txt 就会跟着 dist 一起带过去。使用者安装完包，在 node_modules 里就能找到这个文件，直接喂给 AI 用。

演进路径回顾 ​

整个方案的演进大概是：

手动维护文档
  → 写 Node.js 脚本机械生成（解决了手动的问题，但质量有限）
  → 用 Claude AI 生成（质量上去了，但还是手动触发）
  → 接入 lint-staged git hook（全自动，改代码提交就更新）

最终状态：开发者改了组件 → git commit → lint-staged 自动触发 Claude → llms.txt 更新并一起提交，完全无感。

有什么用 ​

这套东西跑起来之后，最直观的好处是：在让 AI 帮我写涉及内部组件的代码时，先把 llms.txt 贴给它看，生成的代码准确率提升了很多，基本不会出现编造 Props 的情况了。

另外对新人也挺友好的——llms.txt 就是整个组件库的一份高质量速览文档，一个文件看完所有组件的 API。

整体来说这个方案不复杂，核心就是：用 AI 来写给 AI 看的文档，再让 Git Hook 把这个过程自动化。有类似内部组件库的团队可以参考一下。
